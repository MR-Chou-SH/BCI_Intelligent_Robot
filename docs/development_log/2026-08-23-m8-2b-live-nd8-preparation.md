# M8.2b Live ND8 Preparation

Date: 2026-08-23

## Prepared entry point

M8.2b adds one future live command at `integration/m8_selection_cli.py --mode live-nd8`. It does not create a new ND8 reader or decoder. The command reuses the external Windows x64 CPython 3.9 Neurodance environment, `Nd8SerialAdapter(COM11)`, M6.7 channel admission and synthetic warm-up, frozen NumPy FBCCA `LiveOnlineController`, the existing 2-Consecutive final-decision policy, and the completed M8.2a Quest snapshot transport.

The fixed engineering-smoke plan is exactly three trials: slot/class 0 at 7.2 Hz, slot/class 1 at 9 Hz, then slot/class 2 at 12 Hz. Expected classes are stored only as post-hoc evidence and are not supplied to the decoder. Each trial performs the console 13-second preparation countdown, then `selection_open` / Quest ACK, then starts the M6 controller at the next software ND8 packet boundary. Only `LiveOnlineController.stop_trial()`'s immutable final record can submit `eeg_selection`.

## Fail-closed and evidence behavior

The command refuses a non-CPython-3.9 / missing-Neurodance runtime before constructing an ND8 adapter. It records a unique session below the external EEG study root and stops on host/dongle failure, channel-admission failure, ND8 callback/stall/continuity/frozen-channel failure, decoder exception, open rejection, no-decision, invalid final label, final transport failure, or Quest rejection. Raw EEG is written once as the session's M6/ND8 evidence; M8 records store only references and derived selection evidence.

No ND8 streaming acquisition, raw EEG recording or formal trial occurred while preparing this entry point. A test initially reached the adapter's host-MAC readiness query under the real vendor interpreter; it timed out and closed before `start_streaming()`, so it is not hardware acceptance and prompted removal of that environment-dependent test. A no-hardware dry run using the verified external runtime created `D:\EEG_Study\m8_2b-dryrun-20260823T092355Z-51174cb2` with `status=dry_run_passed`, `nd8Started=false`, and the three planned unique selection IDs. The runtime import check confirmed CPython 3.9.13 x64 plus `neuro_dance.core` and `neuro_dance.nd_device_process` imports. This does not establish EEG performance, hardware sample timing, physical optical timing, physical end-to-end latency, or robot behavior.

## Experimental SSVEP display-layout variants — awaiting Quest visual acceptance

Static geometry audit confirmed that the formal M6 scene used three `0.4 × 0.4 × 0.4 m` Unity Cubes (one renderer/material state drives all cube faces), whereas the M8 runtime used one `0.16 × 0.16 m` Quad per slot. Material, `Color.black / Color.white`, alpha and `5/4/3` frame-driven timing remain unchanged.

The M8 diagnostic variant uses a `0.32 m` Quad, a deterministic camera-right separation with a `0.06 m` minimum gap, a `0.24 m` display lift, one non-flashing cyan leader line per slot and a `0.035 m` anchor marker. The line/marker use an independent unlit material and are not passed to the SSVEP controller. The current StableTarget → slot → TargetId authority remains unchanged.

An accepted `selection_open` freezes the currently presented display positions and lines. Final `eeg_selection` and an explicit terminal `selection_abort` release that presentation state; abort also makes a delayed decision terminally rejectable. This compatible lifecycle addition does not send a TargetId from PC or alter class/index resolution. The variant must receive Quest-only visual acceptance before any further M8.2b EEG session, and it must not be described as an accuracy improvement.

The new `ViewLockedHud` presentation mode keeps the same binding and frame-driven renderer but parents only the three SSVEP Quads under an active-camera child. Its updated camera-local positions are `(-0.32, 0.18, 0.85)`, `(0, 0.18, 0.85)`, and `(0.32, 0.18, 0.85)` meters with uniform `0.20 m` scale. Leader lines remain world-space and update their HUD endpoint each frame; target markers remain world-space and carry non-flashing slot numbers `1/2/3`. Before HUD slot assignment, the presentation boundary applies a conservative duplicate gate: same label alone is insufficient; high 2D box overlap and near world position are also required, with deterministic maturity/confidence/TargetId winner selection. Remaining candidates are sorted by camera-right position from left to right. During selection freeze, the binding/line association is held from the existing lifecycle while the HUD root continues following the HMD; live metadata is retained for release-time rebuilding. This spacing and binding update is ready for a new Quest-only visual acceptance and does not claim an EEG-accuracy improvement.

## M8.3 downstream selection-result contract — 2026-08-24

M8.3 keeps Quest as the only authority for class-to-real-target resolution. `BciSelectionTarget` now carries the existing stable-world position when a binding creates the selection snapshot. On exactly one accepted `Resolve`, `BciSelectionCoordinator` creates and publishes immutable `BciTargetSelectionResult` with `selectionId`, predicted class, slot, TargetId, semantic label, frozen world position availability/value, software UTC, and `quest_frozen_selection_snapshot` provenance. `BciSelectionTransportClient.TargetSelected` exposes that event to downstream consumers; it is not sent from PC and is not a robot command schema.

Duplicate, stale, invalid, empty/inactive, no-decision, abort, and reconnect-delivered decisions cannot publish `target_selected`. The selection snapshot is captured after a synchronous HUD assignment refresh, preventing `selection_open` from freezing an older HUD slot view than the immediately visible association. The result's world position remains the software-produced StableTarget anchor snapshot; no scene-reconstruction, grasp pose, or physical-position accuracy claim is added. Software tests cover class/slot resolution, one-shot event publication, frozen TargetId/world-position preservation across live binding changes, and rejection/abort suppression.

## M8.4 implementation — 2026-08-25

M8.4 is implemented and awaiting Quest UX re-acceptance. It leaves M8.3 `BciTargetSelectionResult` unchanged and adds `BciTargetGroupCoordinator` plus a runtime `BciTargetBatchController` only for the frozen `ViewLockedHud` path. The binding already retained a full stable-anchor candidate pool before its previous three-slot truncation, so the implementation reuses its physical duplicate suppression and camera-right left-to-right ordering without changing StableTarget, YOLO, raycast, decoder, or stimulus frequencies.

The outer group freezes up to three candidate anchors in canonical slot `0/1/2` until user submit. An accepted M8.3 result adds the same frozen object to the group in user selection order; the selected slot is made static blue and masked as `TargetInvalid` in subsequent per-decision snapshots, while other slots retain their original frequency/index. Undo restores the original slot to green/flashing. All visible candidates receive minimal state indicators: current available green, selected/submitted blue, and non-current gray; submitted targets add `✓`. A nonempty controller submit creates immutable `ConfirmedTargetBatch`, marks the entire group processed, then allows the next unprocessed group. Right A (or existing index-pinch fallback) submits; right B (or middle-pinch fallback) undoes.

Submit has priority over a pending selection: `BciSelectionTransportClient.AbortPendingSelectionForGroupSubmit` uses the existing M8.3 coordinator abort path before confirming the batch, so a delayed `eeg_selection` is rejected as duplicate/stale. The batch is queued exactly once as a `target_batch_confirmed` message on the existing newline-delimited Quest→PC TCP connection, with batch/group identities, submitted UTC/provenance, and the ordered M8.3 frozen results. `integration/m8_selection_transport/simulated_batch_consumer.py` is a stdlib-only PC mock consumer. This remains a UX/software boundary only; no ND8, robot schema, or robot control is added.

## M8.4 active-group TargetId handover — 2026-08-27

Quest diagnostic logs confirmed that a head turn can make a frozen active-group StableTarget enter `Lost` while the same physical bottle returns through a new tracker TargetId. The strongest observed pair was `target-0002` → `target-0011` (same `bottle` label, approximately `0.012 m` world distance, and one observed bbox IoU of `0.640`). The group itself was not recreated. This implementation adds a group-lifecycle-only logical member with a current TargetId, last valid anchor/time and selected state; it is not a second tracker and does not change StableTarget matching or its missing timeout.

Before an M8.3 selection snapshot opens, a pure reassociation policy considers only same-label, Active, mature, time-continuous and world-continuous candidates. It accepts only isolated one-member/one-candidate matches; any multiple-candidate or multiple-member graph is rejected rather than guessing between adjacent bottles. A successful handover synchronously updates the group coordinator's current member and the binding's slot/indicator/leader-line ownership before HUD indicator refresh. Green and selected Blue state carry to the replacement TargetId, while an already published `BciTargetSelectionResult` and a later `ConfirmedTargetBatch` retain their original immutable frozen selection fact. Selection layout freeze and group submit prohibit handover. Low-frequency `M8_GROUP reassociation_candidate`, `reassociation_accepted`, and `reassociation_rejected_ambiguous` logs provide Quest evidence. M8.4 later completed Quest UX acceptance: the group accumulated selected targets, Submit emitted exactly one ordered `target_batch_confirmed` to the PC consumer, and the group advanced. No ND8, decoder, or robot command was used.

## M8.5 reliable batch-delivery implementation — 2026-08-29

M8.5 adds process-lifetime delivery reliability above the accepted M8.4 batch UX without changing `ConfirmedTargetBatch` or its frozen M8.3 selection facts. Each `target_batch_confirmed` carries its stable `batchId` both at the transport envelope and in the existing payload. Quest keeps an in-memory pending entry until a matching `batch_ack` arrives; a TCP reconnect resends all pending entries in original publish order. The PC simulated consumer deduplicates downstream acceptance by `batchId` but acknowledges every legal receipt, including retries. This is deliberately not durable: a Quest app restart before acknowledgement loses the in-memory pending entry. M8.5 is `Implemented / awaiting simulated reliability acceptance`; no ND8, robot interface, command, database, or queue is added.
