# 厨房 adaptive 采集提速：运行层优化、修复叠加与去重复计算

2026-11-12，分支`feature/data-collection-improve`，基线`0fbf80c`。三个本地提交：`9a29be5`（运行层优化移植）、`cc1951b`（修复叠加、试跑即录制）、`17dedc2`（可选延后重放备份）。未改变模型、物理参数、500Hz物理/25Hz控制、清洗2s/加热5s、成功判据或默认采集模式。

## 结论

同一初态（research seed 0，`faster`，单进程，无图像）下，D09 香蕉＋热狗完整 adaptive 采集：

| 版本 | 采集耗时 | 最终轨迹 | 结果 |
| --- | ---: | ---: | --- |
| 基线`0fbf80c` | 119.87 秒 | 356.52 秒 | 5个高速候选全部失败，`ORIGINAL_FALLBACK` |
| 运行层优化移植 | 85.06 秒 | 356.52 秒 | 同上，备份/最终H5与基线逐元素一致 |
| 修复叠加＋试跑即录制（默认行为） | 91.11 秒 | **101.32 秒** | `OPTIMIZED`，独立重放误差0 |
| 再加`--defer-backup-replay` | **66.02 秒** | **101.32 秒** | 同上，最终H5与上一行逐元素一致 |

L1 苹果：11.03 → 8.16 → 7.22 → **5.25 秒**，最终轨迹均为 8.80 秒（原 28.92 秒）。

采集耗时取最终`report.json`的`wall_seconds`，含首次专家、备份、全部试跑、录制与重放，不含解释器启动。

## 改动

1. **运行层优化移植**：来自`feature/kitchen-linux-task-collection`的接触几何配对缓存、跳过已停用的拒绝判据查询、双臂前馈向量化、NumPy预筛接触、状态录制复用MuJoCo工作区、规划器只请求接触反馈。双臂连续路径未移植（本分支已有自己的双臂连续化）。移植前后苹果与D09的备份H5、最终H5全部数值数据集逐元素相同，5个D09试跑结果一致。
2. **修复叠加**：原优化器只根据第一次失败生成局部修复。D09 的 4 倍候选先因清洗不足失败（`FRUIT_NOT_CLEANED`）；补足清洗后，失败点后移到微波炉按钮：行程 3.6mm 但接触力峰值 0.895N < 1N，加热未启动（`MEAL_NOT_HEATED`）。之后只剩整条 3/2 倍，又在香蕉搬运时触发手指限位审计。现在失败点后移时，在当前修复上叠加新修复（局部限速取更慢者、窗口合并、清洗门控保留），已取得进展的修复先细化，最多 3 层、修复阶段最多 10 次试跑。D09 第 3 次试跑即选中`wash_completion_gate+button_cap1`。
3. **试跑即录制**：原流程先试跑，选中后用同一动作再执行一遍录制。现在可选候选试跑时直接录制，选中后只做独立重放（`verification.json`）；失败候选只删除自己的残缺录制。D09 优化阶段 32.08 → 24.44 秒，录制结果与旧流程重新录制的 H5 逐元素一致。
4. **可选延后重放备份**（`--defer-backup-replay`，仅 adaptive，默认关闭）：备份完成原生执行与最终成功判定后标记`EXECUTED_REPLAY_PENDING`，暂不重放。高速轨迹被选中时备份只作动作来源（`backup_replay: NOT_REQUIRED`）；回退采用备份前必须补做独立重放，失败则该 attempt 失败；续跑校验此重放记录。D09 备份阶段的 25 秒重放因此省去。用真实苹果样本强制回退，补做重放误差为 0，续跑只读。

## 长任务验证

最终配置（adaptive＋`--defer-backup-replay`，每样本 1 次尝试，不换 seed），2 个进程：

| 任务 | seed | 原轨迹 → 最终 | 采集耗时 | 选中修复 |
| --- | ---: | ---: | ---: | --- |
| C04 热狗 | 0 | 183.20 → 52.92 秒 | 33.2 秒 | `button_cap1` |
| C08 香蕉＋热狗 | 0 | 292.20 → 83.64 秒 | 55.6 秒 | 清洗门控＋按钮原速（叠加） |
| C08 梨＋汉堡 | 0 | 273.20 → 79.00 秒 | 48.0 秒 | 清洗门控＋按钮原速（叠加） |
| D05 汉堡 | 0 | 241.52 → 68.92 秒 | 42.2 秒 | `button_cap1` |
| D08 番茄＋热狗 | 0 | 269.32 → 77.60 秒 | 48.7 秒 | `button_cap1` |
| D09 苹果＋汉堡 | 0 | 326.28 → 93.68 秒 | 60.0 秒 | 清洗门控＋按钮原速（叠加） |
| D09 香蕉＋热狗 | 2 | 361.16 → 102.64 秒 | 61.5 秒 | 清洗门控＋按钮原速（叠加） |
| D09 香蕉＋热狗 | 1 | — | — | 首次专家规划失败 |

7/8 合格且全部`OPTIMIZED`，整任务缩短 3.46–3.52 倍，独立重放 qpos/qvel 误差均为 0；4 条依赖修复叠加：旧逻辑不会生成这类组合，只能继续试整条 3/2 倍或回退（仅 D09 香蕉＋热狗 seed 0 实测了旧逻辑结果）。两进程并行的耗时会受 CPU 竞争影响，仅作量级参考。

D09 香蕉＋热狗 seed 1 在首次专家阶段失败：`fruit_legacy_place: IK_FAILED`（洗后放回篮子的位置无 IK 解）。用未修改的`0fbf80c`重跑同一 seed 得到相同错误与数值，属于既有规划局限，不是本次改动引入；正式采集默认 3 次尝试会换 seed。

## 验证与边界

- Kitchen 回归 **172/172 PASS**（新增修复叠加、深度上限、无进展不叠加、试跑即录制只重放一次、续跑不重复、失败录制清理、延后重放的选中/回退/重放失败/开关校验/中断续跑）。
- 只验证上表固定初态，不代表全目录或任意随机初态；全目录批次尚未用新代码重跑。
- `continuous`模式未修改，仍是先试跑再重新录制。
- 测量前本机曾因内存超频（EXPO）出现页面缓存损坏与跨进程崩溃，恢复 BIOS 默认后才开始本轮测量；资产与依赖文件已逐一核对。

## 审阅视频主视角

审阅视频默认主视角改为`v3_main55`：1600×900、方位正对、俯角55°。相机位置由框选计算得到：取全部水果、主食及餐盒、托盘、水槽、篮子、水龙头、微波炉、送餐桌桌面，以及九条加速长任务中双臂全过程的实际可见网格顶点，在固定朝向下求能包含它们的最近位置（边距3%），并把多余高度留在前景以压低上方黑边。上沿由右臂抬到最高时决定，下沿由送餐桌前沿决定；在45°视场下上沿视线越过4m×4m地板，因而改用30°视场。它是审阅用自由相机，只在回放副本上设置视场，不改模型和重放身份；`v3_front`仍可显式选择。

同一D09轨迹四个时刻对比：原`v3_front`（960×540，缩放0.9）黑色背景61.1%、任务元素像素11.7%；新主视角黑色背景17.5%、任务元素像素19.0%。剩余黑色是地板以外的区域，位于上方窄带和两角。加速后D09（101.32秒）的视频为`experiments/kitchen_platform_v3/videos_main55_20261112/videos/kitchen_expert_v3_D09_banana_hotdog/sample_01/render_001/trajectory.mp4`，1600×900、25fps、2533帧，完整解码通过，源轨迹哈希与采集报告一致；它是已记录状态的回放，不是训练图像。
