# M13.6 MuJoCo ↔ Quest Real-Time Visual Sync

## Software architecture

MuJoCo remains the sole simulation authority. The existing reliable TCP
selection/control path on port `11001` is unchanged. M13.6 adds a separate
PC→Quest visual latest-state-wins stream on port `11002` with independent
transport modes:

- `udp` — preferred normal-LAN datagram mode;
- `tcp` — compatibility mode for networks that block peer UDP, using one
  persistent newline-delimited JSON connection with `TCP_NODELAY`;
- `auto` — Quest receiver mode that accepts either UDP or TCP on the visual
  port. The two transports remain separate from M8 control and duplicate
  sequence values are suppressed by the existing sequence gate.

TCP `11002` and UDP `11002` are separate protocol namespaces; neither changes
M8 control TCP `11001`.

Each startup/full-state frame contains:

- protocol and mapping version;
- monotonically increasing sequence and MuJoCo simulation timestamp;
- seven FR3 joint positions in radians;
- both UMI finger slider positions and opening value;
- robot base pose;
- all four block poses keyed by frozen `logicalBlockId`.

No mesh, planner trajectory, EEG, or internal simulator object name is sent.

## Coordinate mapping

`MujocoToQuestTransform` is one shared transform for robot base and blocks:

- MuJoCo table top `z=0.75 m` maps to Quest workspace local `y=0`;
- uniform scale `0.70` matches the existing M9 visual scale;
- MuJoCo Z-up is converted to Unity Y-up using the existing `-90°` X basis;
- Quest world origin remains the M9 workspace/table reference, never the HMD.

The current MuJoCo table is `1.20 × 0.80 m`; the current Quest visual table is
`0.96 × 0.56 m`. Block dimensions and initial positions also differ. This is
an explicit visual calibration limitation, not a reason to modify MuJoCo. The
first Quest observation must determine whether the chosen uniform scale and
world reference need a bounded calibration value.

## Quest receiver

`M13_6VisualSyncReceiver` receives on background UDP/TCP transport threads,
validates the protocol and full four-block snapshot, rejects stale/duplicate
sequence values, and replaces pending packets so a slow render thread cannot
build a historical animation backlog. It applies only the newest state on
Unity's main `Update()` loop. It uses a short interpolation interval for
joint/position smoothing and quaternion Slerp for rotations. On disconnect,
the last valid pose remains in place. TCP accepted clients use
`TCP_NODELAY`.

`M13_6VisualSyncAutoInstaller` adds the receiver only to an M9 runtime scene.
Selection identity, frozen snapshots, and the M8 TCP lifecycle remain outside
the receiver. Optional telemetry is debug-only and disabled by default.


## USB/ADB engineering commands

With Quest connected by authorized ADB USB, the dedicated visual forward is
localhost 21002 to Quest TCP 11002. It never forwards or writes M8 control
TCP 11001:

    python -m integration.m13_6_usb_visual_acceptance --mode synthetic --duration-seconds 10
    python -m integration.m13_6_usb_visual_acceptance --mode single --logical-block-id block_sim_01
    python -m integration.m13_6_usb_visual_acceptance --mode sequential

The future Wi-Fi preflight is:

    python -m integration.m13_6_visual_preflight --probe

The USB runner records machine-readable reports under artifacts/, including
ADB state, forward mapping, Quest socket state, sender counts, MuJoCo results
and filtered M13_6_VISUAL log lines. MuJoCo stream helpers accept an optional
start_sequence so a sender reconnect can continue monotonically instead of
replaying sequence zero into a still-running receiver.

The receiver emits a bounded debug summary approximately every five seconds
when the diagnostic build is deployed. The summary includes transport
lifecycle, received/accepted/applied counts, stale/duplicate/malformed
counts, latest-state replacements, effective receive rate, last sequence and
scene binding status. It is intentionally not a per-frame log.

The software-only transform sanity report is:

    python -m integration.m13_6_transform_sanity --source synthetic --frames 180
    python -m integration.m13_6_transform_sanity --source mujoco

It checks finite values, monotonic sequence, quaternion norms, joint ranges,
position/angular jumps and block workspace bounds. It cannot establish visual
alignment in the headset.

the current P70 hotspot path remains a transport limitation unless the

## Final return-to-lab compression

The only required software build action is one human Unity GUI action:

1. Open the already licensed Unity `6000.0.66f2` project and click **Build And Run** for the M9 Android scene.
2. From the repository root run one verification command:

       .venv\Scripts\python.exe -B -m integration.m13_6_post_build_verify --probe --output artifacts\m13_6_post_build_verify.json

The verifier records APK mtime/SHA-256/package/version, compares the APK with
the receiver/scene source timestamps, launches the package, recreates the USB
forward, checks TCP/UDP `11002`, sends a short synthetic probe and requires
periodic diagnostics plus binding evidence. Binding evidence may be the
dedicated `scene_bindings` line or the receiver's periodic `bindings=True`
field; this avoids a false failure when the one-shot scene line has rolled out
of the retained logcat window. It returns `STALE_SOURCE_BUILD` instead of
silently accepting an old APK.

For final human visual acceptance, use one entry point after putting on the
headset:

       .venv\Scripts\python.exe -B -m integration.m13_6_visual_demo --transport usb --phase all --human

The six questions are only: (1) robot/table/block spatial relationship, (2)
joint directions, (3) gripper open/close, (4) block grab/follow/place, (5)
continuous motion without visible jumps, and (6) no unacceptable accumulated
latency. The launcher saves per-phase PC/MuJoCo/Quest log observations but
never self-declares visual PASS. For a same-LAN return, replace `usb` with
`wifi`; it discovers the Quest IP and verifies TCP `11002` without manual IP
entry. USB `21002 -> 11002` remains the engineering/debug fallback.

The tested P70 note is deliberately narrow: historical M8 TCP `11001` worked;
PC→Quest UDP peer delivery was not observed in the tested session; TCP visual
compatibility is the chosen path. This does not claim that P70 universally
blocks UDP.

## Short failure recovery table

| Symptom | Minimal safe response |
|---|---|
| Control TCP `11001` down | Stop the trial, verify the existing M8 baseline path; do not merge visual traffic into `11001`. |
| Visual TCP `11002` down | Relaunch the Quest package, recreate USB forward or rerun Wi-Fi preflight, then rerun post-build verify. |
| Quest app sleeps/exits | Relaunch the package and confirm the listener before sending; do not infer a visual result. |
| ND8/COM11 cannot open | Stop the live attempt; preserve logs and use the approved runtime/port procedure; no retry loop or fallback to fabricated EEG. |
| Host-MAC callback timeout | Stop active mode, keep baseline/shadow evidence, and resolve the approved external ND8 runtime first. |
| Channel quality fails | Do not start M13 active; repeat physical preparation/quality check under the approved protocol. |
| MuJoCo action fails | Preserve the trial as failed; do not advance task state or count an M10 commit. |
| Quest TargetInvalid/selection mismatch | Abort the selection, refresh the frozen snapshot and retry only through the existing lifecycle; never fabricate a target. |

## Visual alignment source repair (requires a new Unity build)

The first alignment audit found two independent coordinate problems and one
MuJoCo sequential-placement problem:

- the receiver was applying the telemetry base pose to `FrankaRoot` every
  frame, so the robot could jump away from the scene's tracked workspace
  anchor;
- the synthetic block fixture used a narrow MuJoCo-style cluster instead of
  the Quest catalog's explicit `[-0.32, -0.105, 0.105, 0.32]` table layout;
- the four sequential MuJoCo planners released blocks into one shared area,
  allowing later bodies to disturb earlier placements.

The source repair keeps the existing transport and joint mapping, but pins the
Quest robot to its scene anchor, applies block motion as a table-relative delta
from the initial catalog pose, makes the synthetic fixture invert the same
transform, and gives only the M13.6 four-block stream separated 2x2 placement
centres. The default single-block planner behavior is unchanged. No Unity
scene file was rewritten by this repair.

Source-level evidence: the receiver has balanced C# braces, no per-frame
`FrankaRoot` position/rotation assignment, and explicit
`fixed_scene_anchor`/`table_relative_baseline` diagnostics. The Python core
stream and USB fixture tests are 15/15; M9/M10/M14 related tests are 31/31;
synthetic and MuJoCo transform sanity reports are PASS. The current installed
APK was rebuilt after this source repair and its post-build verifier passed;
Quest visual alignment is still pending user-worn observation. The subsequent
motion playback/sequence repair is Python-only and does not require another
Unity build.

## Motion regression diagnosis and playback repair

After the alignment repair was deployed, the user reported correct robot/table
and initial block placement but no visible motion. The captured demo evidence
identified a sender-side sequence failure, not an alignment regression: the
old full demo started at sequence `0`, while the Quest receiver had already
accepted through `200089` during the post-build probe. Its later single and
four-block frames were therefore received but rejected as stale; diagnostics
remained at `accepted=90`, `applied=90`, `lastSeq=200089` while stale and
replacement counts increased.

The demo launcher now seeds a new run above the retained Quest sequence (or
uses an explicit override), records each phase's run metadata, prompts before
the phase starts in `--human` mode, and adds a separate slow single-joint
diagnostic. MuJoCo single and sequential playback can now be explicitly paced
on the wall clock at the configured 30/60 Hz instead of dumping an offline
planner trajectory at maximum speed. Latest-state replacement remains intact.

Software evidence: the single-joint fixture produces q1
`0 -> +0.35 -> 0 -> -0.35 -> 0`; its sender report records 240 frames at
30 Hz with no sender error. A real software MuJoCo single replay emitted 208
frames with `realtimePlayback=true` in 7.94 s (expected frame interval budget
approximately 6.90 s), and returned `place_ok`. The receiver source still
contains the seven-joint `ApplyFrame` loop and no root-motion early return.

The remaining check is deliberately small: the user must wear Quest and run
only the single-joint diagnostic first. A full pick/place demo is not used as
the next regression probe until that motion is visibly confirmed.

## Final visual polish: base-frame calibration and phase continuity

The MuJoCo frame audit is now explicit rather than inferred from the observed
image. The `base` body is at `(0, 0.4, 0.75)` with an identity quaternion, and
the table-centre direction is MuJoCo `-Y`. The existing `R_x(-90°)` Z-up to
Unity Y-up basis maps that direction to Quest local `+Z`, while the Quest
`LeftRobotAnchor` is placed at the rear table edge and must face local `-Z`.
The M13.6 receiver therefore applies one fixed `180°` yaw in the table frame
when it first resolves `FrankaRoot`; it does not move the root, alter joint
order/signs, or modify the MuJoCo planner. Diagnostics identify this as
`robot_frame_calibration=yaw_180_table_frame`.

The visual MuJoCo sampler now supports an explicit phase-start block anchor.
For M13.6 visual playback it captures the raw phase-start block pose and emits
`visual_anchor + (current - phase_start)` for each frozen logical block. The
runner also records the raw MuJoCo terminal pose separately. The visual demo
uses the prior phase's mapped terminal pose as the next visual anchor and the
prior phase's raw terminal pose as the next MuJoCo initial state; this prevents
the same displacement from being applied twice. The software rehearsal
measured a Phase 2 → Phase 3 first-frame maximum jump of `0.0` in the rebased
MuJoCo frame. This is opt-in visual alignment metadata; default M9/M10 planner
behavior is unchanged.

The current default MuJoCo source layout and the Quest catalog are not the same
four-point layout. The M13.6 visual runner now uses a separate, explicit
visual-only set of four placement centres and a small visual placement region;
the default M9/M14 `GripperGraspPlanner` placement remains unchanged. In the
software rehearsal the final mapped Quest positions formed two compact
columns: approximately `x=-0.158/-0.165` and `x=0.158/0.160`, with each
column's depth spread below `0.01 m`. This removes the prior source-layout
artifact from the visual stream without changing planner semantics. The
Phase 2 → Phase 3 first-frame jump remained `0.0` in the rebased frame
coordinates.

Because the receiver C# source changed, the next interactive gate requires a
new Unity Build And Run followed by `m13_6_post_build_verify --probe` before the
full human visual demo. ND8, COM11, EEG and physical robot operation remain
out of scope.

## Final root-cause repair: unified table frame and physical stacking

The earlier anchor/yaw workaround is superseded by one shared
`MujocoToQuestTransform`. `M13_6VisualSyncReceiver` no longer applies an
independent 180-degree robot correction or per-block calibration. Robot,
gripper, and every logical block now use the same table-frame basis; the
MuJoCo robot-base orientation is converted through that basis and the Quest
scene root remains the fixed scene anchor. This keeps the frozen logical
mapping and M8 selection lifecycle unchanged.

The old flat 2x2 placement fixture is superseded for the M13.6 visual demo.
The visual runner now resolves geometry-derived targets for two physical
stacks: red bottom/green top and blue bottom/yellow top. Resting blocks use a
separate collision category, the active grasp uses the robot-compatible
category, and the category is switched at release so later arm motion cannot
knock over completed stacks. The visual execution order places both bottom
blocks before the top blocks. Legacy M9/M10 planner defaults are unchanged.

The software evidence includes actual MuJoCo body poses, gripper-to-block
relative-pose checks, contact counts, penetration depth, horizontal alignment,
vertical gap, tilt, and residual speed. The final four-block replay returned
`4/4 place_ok`; both stack pairs had contact, less than 0.001 m penetration,
less than 0.01 m horizontal error, less than 0.001 m vertical gap, and stable
residual speed. These are software/physics checks, not human Quest visual
acceptance. Because the Unity receiver and block catalog changed, a fresh
Unity Build And Run is required before the next Quest observation.
